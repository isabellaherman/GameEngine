1. Where export lives outside the runtime, inside the project

Gregory's book splits an engine into the runtime (what ships inside the game) and the tools (what makes the game: editor, asset pipeline, build). Export is a tool. It reads the engine and the game, and writes something a player can run; it never ships inside that thing. So it gets its own folder beside engine/ and editor/, and the runtime never imports it.

engine/ · runtime

  • World, camera, math
  • Renderer
  • Ships inside every game

editor/ · tools

  • Editor Defaults, gizmo
  • Accessibility settings
  • Never ships to players

export/ · tools (not yet)

  • export/web: the page, bundle, assets
  • export/native: Bend → C → binary
  • Reads engine and game; ships nothing of itself

Figure 1. Export sits with the tools. Arrows only point into the runtime, never out of it.

Figure 2. The web export, step by step. Steps 1–3 already run; step 4 is needed as soon as the game has assets; 5–6 work but are manual.

A web game is static: no server runs game code, so every step ends in plain files. That is why the engine can host it itself: publishing a game is storing a folder and giving it a link. A server only appears later, for accounts, saves in the cloud or multiplayer.

4. WebGL vs WebGPU vs a Unity-style build

Two separate questions hide here. How the engine reaches the browser: as its own code (like three.js) or as a whole engine runtime compiled to WebAssembly (like Unity). And which GPU API it draws with: WebGL2 or WebGPU.

Reading: the engine already takes the three.js road, which is the right one for the web. For the API, stay on WebGL2 now and add WebGPU later as a second backend with WebGL2 as the fallback, the way three.js does. Because the math lives in Bend, only the drawing layer (main.js) would change.

5. Publishing, modeled on Vercel a reference, not a host

Vercel is not used here. It is studied because its deploy is the experience the engine should give to whoever makes a game: one action, a link, safe to share, easy to undo.

1PushA commit on GitHub, or vercel deploy from a terminal.
→
2BuildA clean machine clones the repo, detects the framework, installs, runs the build.
→
3Build OutputEverything lands in one agreed folder shape..vercel/output/
→
4UploadFiles are stored by content hash; unchanged files aren't sent again.
→
5DeploymentImmutable, with its own permanent URL. Every push gets a preview.
→
6AliasThe domain is pointed at a deployment. Rollback = point it back.
→
7EdgeStatic files cached near players; functions run only on request.

Figure 4. Vercel's deploy, from a push to a cached page: the reference.

What makes it easy is three agreements. The Build Output API: any tool that writes .vercel/output/ (a static/ folder, optional functions/, a config.json) gets deployed, whatever framework made it. Immutability: a deployment never changes, so a preview link is safe to share and going live is only moving a pointer. Git as the trigger: no "deploy" step to remember; a push is a deploy.

What the engine takes from it, for games:

VercelIn the engine
Build Output APIOne agreed game folder that export/web always writes: page, bundle, assets, manifest. Anything that writes it can be published.
Content-hash uploadAssets named by hash; publishing again sends only what changed.
Immutable deploymentEvery publish of a game is a fixed version with its own link, never overwritten.
Preview per pushEvery save of a game can produce a playable preview link.
AliasThe game's public link points at one version. Going live or rolling back is moving that pointer.
Edge cacheStatic game files served from a CDN near players.

6. How agents publish a game Vercel's model, applied to the engine

In Vercel an agent has three doors, all ending at the same API: the CLI, the SDK / REST API, and an MCP server with tools to read docs, list deployments, read logs and deploy. A claimable deployment lets an agent publish first and hand ownership to a person through a link. The engine can offer the same doors for games: its own CLI, API and MCP server, so an agent can check, build and publish a game, while going live stays with the person.

7. Native and consoles the long road

→
3Platform layerWindow, input, audio, file paths, the graphics API of each platform.
→
4Platform SDKEach console's compiler, libraries and dev kit, under NDA.
→
5CertificationThe platform holder tests and approves the build.

Figure 6. From Bend to a console. Steps 4–5 belong to Nintendo, Sony and Microsoft.

Consoles cannot be reached by open tools alone. Godot's documentation states that no engine may distribute console export templates without the user proving they are a licensed developer, because of the platform holders' NDAs. Many studios outsource the port. What the engine can do now is keep its layers clean, so that the platform layer is the only thing a port has to write: logic in Bend, drawing and input behind a thin layer, as it already is on the web.

8. Suggested order

  1. Web, static, by hand. Done: dist/ on GitHub Pages.
  2. export/web. One command: check, build, hash file names, write a manifest, produce dist/. Laws for it: nothing ships if a law fails; every file in the manifest exists.
  3. Asset conditioning. When the first model or texture arrives: GLB, KTX2, Opus.
  4. Engine publish. Immutable versions, preview links, a public link that is a pointer; then the CLI and MCP doors for agents.
  5. WebGPU backend beside WebGL2, chosen at load time.
  6. export/native. Desktop through Bend → C and Metal, using Bend's own window and audio.
  7. Consoles, once there is a game and a platform license.
